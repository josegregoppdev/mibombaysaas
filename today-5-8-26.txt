# Today — 2026-08-05

Session log: controller refactor — "controller calls services, not repositories" + "view always works with DTOs".

## Objective
- Apply the **Spring MVC + DTOs and thin controllers** rule to every controller in the project.
- Remove all `Repository` fields from controllers. Controllers must call services only.
- Stop passing JPA entities to Thymeleaf views. Views receive DTOs only.
- Move business logic (validation, mutations, persistence) from controllers into services.
- Rename `CompanyRegistrationService` → `CompanyService` (it is now a general service, not just for registration).
- Add a new `UserService` to centralize user lookups and the password-change logic.

## Important Details
- Java 21, Spring Boot 4.1.0, Thymeleaf, Bootstrap 5.3, MySQL, MapStruct, Lombok.
- User communicates in English (B1 level, some typos).
- The rule (added to `AGENTS.md`): "Spring MVC + DTOs and thin controllers. The form/view ALWAYS works with DTOs, never with JPA entities. Services return DTOs. The controller calls services, never repositories. **Business logic lives in the service layer**, not in the controller. The controller only does presentation."
- The `UserService` is the only service that touches the `UserRepository` (for user lookups + password change). The `CompanyService` is the only service that touches the `CompanyRepository` (for registration + lookups + listing all companies).
- `CompanyDTOResponse` was extended in two steps: first with `name`, `email`, `phone`, `address` (for the dashboard), then with `subdomain`, `active`, `createdAt` (for the admin companies list). The `CompanyMapper.toResponse(Company)` now maps all these fields automatically.
- `UserDTOResponse` got one extra field: `mustChangePassword` (Boolean) — needed by the `DashboardController` to enforce the "redirect to change-password" rule from the DTO.
- No database migration. No template changes (the DTOs have the exact field names the templates already used).
- The `PasswordChangeController` now throws/catches `IllegalArgumentException` from the service to show the error (instead of doing the business logic itself).
